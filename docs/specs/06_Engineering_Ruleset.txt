ENGINEERING RULESET
===================

This file is normative. GitHub owns work status; archived reports own historical
measurements. The rules below describe the implementation shape that must remain true.

Rule #1 — Managed and SQL layers orchestrate; native code computes
------------------------------------------------------------------

C# and SQL own lifecycle, transactions, binding, and composition of operations. Native
C/C++ owns byte-level codecs, geometry, hashing, ranking kernels, traversal, dense
contractions, and other heavy loops. Moving a hot loop into a different orchestration
syntax is not an optimization.

Rule #2 — Preserve planner-visible SQL
--------------------------------------

SQL intended for inlining must satisfy the applicable PostgreSQL inliner contract.
KNN comparison points reach the planner as bound parameters. `STRICT`, function-local
`SET`, procedural bodies, blocking CTEs, and wrappers are evaluated by measurement and
`EXPLAIN`, not assumption.

Rule #3 — Reduce before expanding
---------------------------------

Apply indexed identity, relation, source, context, and band constraints before fan-out.
Do not create cartesian candidates and repair them with a final `LIMIT`. Result limits
require a ranking produced by the evidence model.

Rule #4 — Query the installed typed surface
--------------------------------------------

Use `api('<substring>')` to discover installed operations before writing SQL against
substrate tables. Prefer canonical helpers and `_approx` operational reads when exact
counts are unnecessary. Validate schema claims against installed DDL/functions and
performance claims against representative degree and seed profiles.

Rule #5 — Batch instead of row-by-row calls
-------------------------------------------

Resolve, realize, score, and write in bounded batches. Aggregate ids first, then call
batch/native operations. Per-row set-returning functions, repeated name resolution,
string rendering, and managed/native crossings are defects on scalable paths.

Rule #6 — One implementation per fact
-------------------------------------

Identity, relation resolution, ranking, rendering, traversal, folding, and realization
each have one canonical implementation. A second body requires a documented semantic
or performance reason and parity tests. Compatibility wrappers delegate; they do not
reimplement.

Rule #7 — Native replacements use explicit contracts
----------------------------------------------------

When a native operation replaces a SQL reference path, its name, input domain, output
order, null/unknown behavior, score equation, and parity test are explicit. Suffixes
such as `_fast` do not excuse semantic drift.

Rule #8 — Ingest is one ordered spine
--------------------------------------

The ingest sequence is:

`unpack → records → working-set dedup → accumulation → bulk tier descent → apply/COPY → fold completion`

Decomposers are pure content-to-`SubstrateChange` streams and contain no inline SQL.
They declare every relation they emit. The shared spine owns batching, novelty proof,
tier descent, COPY, attestation merge, consensus fold, and completion semantics. The
right operation at the wrong stage violates this rule.

Rule #9 — The CLI is a server workload
--------------------------------------

Long ingest/export commands use server GC, bounded memory, structured progress, and
cancellation-safe journals. Summary output is not verification; each command has an
independent acceptance read.

Rule #10 — Parallel stages are bounded and deterministic
--------------------------------------------------------

Parallel producers communicate through bounded channels. Outer index-build concurrency
remains one unless a measured design proves safe. Per-cell non-commutative folds retain
FIFO ordering; commutative deposits may run concurrently.

Rule #11 — Diagnose with independent evidence
---------------------------------------------

Measure wall time, CPU, waits, allocations, database plans, lock state, and phase
throughput at the layer that owns the claim. Do not infer a bottleneck from one metric
or validate a populated-system claim with an empty fixture.

Rule #12 — Defaults derive from source and machine
--------------------------------------------------

Batch, commit, and working-set sizing derive from source shape and machine capacity.
Environment overrides are diagnostic controls, not product defaults.

Rule #13 — Fence expensive STABLE calls deliberately
-----------------------------------------------------

PostgreSQL does not constant-fold a STABLE function into one execution for the whole
query. A call in a filter can therefore execute once per candidate row. An indexed
`= ANY(fn())` predicate may become a one-shot index condition; `<> ALL(fn())` and an
ordinary filter do not provide that guarantee. A pull-up-eligible one-row subquery is
not a fence. Use a MATERIALIZED CTE when an expensive stable set must be computed once,
and prove the call count and plan with representative `EXPLAIN (ANALYZE, BUFFERS)`.

Rule #14 — Serving rows carry ids with labels
----------------------------------------------

A human- or UI-facing serving operation returns the content id and its display label
in the same row. Machine-hop, fold, and internal set-returning operations return ids
and let the caller batch realization at the edge. Never call `realize` or `render_text`
once per row when a batch form exists. Every table-returning operation declares which
of these two shapes it serves.

Rule #15 — CTE materialization is explicit
-------------------------------------------

Every CTE in a serving SQL body declares MATERIALIZED or NOT MATERIALIZED. Use
MATERIALIZED for sets that must be evaluated once or must resist predicate pull-up;
use NOT MATERIALIZED for a pure relational expression the planner should inline. The
keyword documents and enforces the intended evaluation boundary.

Operational constraints
-----------------------

- One ingest at a time. Never kill an ingest or backend owned by another task.
- Never reset or drop the database without explicit authorization for that action.
- PostgreSQL lifecycle is service-managed; do not start the live cluster with `pg_ctl`.
- After an engine rebuild, rebuild and install extensions before verification.
- `pg_regress` validates the installed extension, not an edited template.
- Do not edit an executing Windows batch file.
- Preserve unrelated worktree changes; use isolated worktrees and explicit staging.
