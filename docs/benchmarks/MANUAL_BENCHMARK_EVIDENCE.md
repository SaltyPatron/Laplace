# Laplace benchmark suite

Tracking: `#1432`, `#1436`, `#1451`, `#1561`.

`.github/workflows/benchmark-evidence.yml` is deliberately `workflow_dispatch`-only. Long measurements are evidence, calibration, capacity, billing-estimator and optimization inputs; they are not automatic source-push or pull-request gates.

The workflow is only the dispatcher. Benchmark meaning lives in versioned source:

- `scripts/benchmark-profiles.json` — named profiles and suites;
- `scripts/benchmark_suite.py` — registry validator, suite runner and suite receipt;
- `scripts/benchmark_scale_plan.py` — managed-host serviceable/saturation worker planning;
- `scripts/bench-compose.py` — conservative one-worker composition floor;
- `scripts/bench-compose-scale.py` — finite unique-corpus/file-grain scaling diagnostic;
- `scripts/bench-compose-stream-scale.py` — aggregate independent-stream scaling;
- `scripts/bench-forward-program.py` — installed canonical forward-program work benchmark;
- `scripts/benchmark-forward-cases.json` — versioned prompt/hops/fanout query matrix.

## Current suites

| Suite | Profiles | Purpose |
|---|---|---|
| `quick` | `core-single`, `moby-roundtrip` | conservative core floor + bit-perfect realization proof |
| `throughput` | `core-single`, `core-scale-streams` | one-worker floor + aggregate serviceable stream scaling |
| `core` | `core-single` | one-worker native composition |
| `scale` | `core-scale-streams` | aggregate independent-stream scaling |
| `moby` | `moby-roundtrip` | bit-perfect Moby Dick engine roundtrip |
| `query` | `query-forward` | exact-installed-runtime canonical forward-program work receipts |
| `all` | source/core profiles except `query-forward` | composition/scaling/roundtrip evidence without mutating or requiring installation |

`query` is intentionally explicit rather than silently included in `all`. The source/core profiles can benchmark an arbitrary selected ref without installing it. A database-backed cognition measurement is valid only when the installed extension/execution module is the exact content-versioned runtime built from the selected source. The query harness refuses a mismatch rather than measuring stale production code and labeling it with the checked-out SHA.

Future storage, full-corpus admission, GPU/provider, model export, competitor-equivalent accepted-work and calibrated wall-energy profiles belong in this same registry with their own declared execution/state boundaries.

## Exact-artifact and exact-runtime law

A benchmark of source revision `X` must execute the artifact/runtime derived from `X`.

Source/core profiles explicitly bind:

```text
build/engine/core/liblaplace_core.so
build/engine/core/perfcache/laplace_t0_perfcache.bin
```

through `LAPLACE_CORE`, `LAPLACE_T0`, `LAPLACE_PERFCACHE_BIN`, `LAPLACE_ENGINE_BUILD` and build-tree `LD_LIBRARY_PATH`. SHA-256 digests are retained.

The database-backed query profile additionally binds the exact content-derived extension identities generated by the selected build:

```text
build/extension/laplace_substrate/laplace_substrate.control
build/extension/laplace_substrate/laplace_execution_module.txt
```

`laplace_substrate` derives `EXT_VERSION` from the SQL manifests, SQL/control inputs and the content-versioned execution-module name. The execution module itself is named `laplace_execution_<content-hash-prefix>` from its native sources/headers/compiler/ISA inputs.

Before one query measurement is accepted, `scripts/bench-forward-program.py` proves:

```text
installed pg_extension.extversion == built laplace_substrate default_version
and
generation.forward_program has exactly one C binding
and
that pg_proc.probin == the built laplace_execution_<...> module
```

A mismatch is a benchmark failure. Source identity is not execution identity until the receipt proves the binding.

## Profile: `core-single`

`scripts/bench-compose.py` measures the native core boundary only: UTF-8 input, Unicode/NFC handling, UAX #29 segmentation, content/Merkle identity construction, tier-tree composition and geometric placement. It includes no PostgreSQL, COPY, network, API serving or GPU work.

It is a **measured one-worker floor**, not a whole-machine claim. Never derive host throughput by multiplying this rate by a core/thread count.

The 4-character BPE-equivalent value is a familiar input-rate normalization only. It is not the structural work amount. Every accepted run emits exact machine-readable work lines:

```text
WORK_INPUT documents=<n> bytes=<n> codepoints=<n>
WORK_SHAPE tier_tree_nodes=<n> nodes_per_codepoint=<x> nodes_per_tok4=<y> chars_per_tok4=4
```

The harness rejects a run if any document is rejected by native composition or if the exact node count changes across repeats. `benchmark_suite.py` independently reconciles the reported amplification ratios against exact counts before sealing `suite-receipt.json`.

Historical committed evidence from `0f8405938daf3ab2aa6c1b745823be9e991ce6e6` recorded roughly:

```text
1.859M codepoints/s
464.8k 4-char BPE-equivalent input units/s
4.555M tier-tree nodes/s
```

single-threaded.

Run `34823625126` later measured, before its unsafe 12-logical-CPU scale point:

```text
51,223,726 codepoints
125,793,955 tier-tree nodes

best single thread:
1.7615M codepoints/s
440.4k 4-char BPE-equivalent input units/s
4.3259M tier-tree nodes/s
```

Its exact structural amplification is:

```text
125,793,955 / 51,223,726
  = 2.455775181... tier-tree nodes / codepoint
  = 9.823100724... tier-tree nodes / 4-char token-equivalent
```

Reducing that run to `440.4k tokens/s` hides the fact that the same measured interval constructed about **4.33 million exact structural nodes/s**. The normalized token-equivalent is useful for comparison intuition; the exact input/node receipt is authority.

## Scaling profiles

`core-scale` and `core-scale-streams` answer different questions.

`core-scale` measures one finite corpus partitioned at whole-file grain. It exposes coarse scheduler/makespan behavior; it is not a whole-machine ceiling and not proof that one semantic DAG uses several workers.

`core-scale-streams` gives each worker one complete real-corpus stream, so measured work grows with worker count. It measures aggregate concurrent composition capacity. It likewise does not prove single-object internal parallelism; #1451 owns that missing proof.

See `docs/benchmarks/SCALING_MODES.md` for the distinction.

## Managed-host capacity law

The self-hosted runner is a managed machine, not a disposable benchmark appliance. PostgreSQL, Actions, product services and control/monitoring processes require headroom.

The workflow therefore resolves a scale plan before either scaling harness. Defaults are:

```text
allow_saturation = false
reserve_logical_cpus = 2
```

On the known 6C/12T i7-6850K host the normal plan resolves to:

```text
1,2,3,4,6,8,10
```

A point above the serviceable ceiling is rejected unless the dispatch explicitly sets `allow_saturation=true`. Saturation results are labeled separately.

Run `34823625126` remains an incomplete/failing counterexample from the earlier design: its series admitted all 12 logical CPUs and no sealed final evidence artifact was available. The retained evidence does not establish a stronger terminal-cause claim, so none is invented.

The headroom repair is now in source; a fresh managed-host serviceable run is still required before quoting a new measured serviceable-capacity number.

## Profile: `moby-roundtrip`

`laplace roundtrip <file> [out]` measures engine text decomposition/reconstruction. The suite independently verifies output bytes and SHA-256 rather than trusting the CLI success message.

This remains distinct from database-backed deposit/reconstruction because persistence is additional work and must not be blended silently into the core number.

## Profile: `query-forward`

`query-forward` benchmarks the installed canonical `generation.forward_program(...)` surface rather than a private toy query.

The profile is read-only and refuses to run while an ingest is visibly advancing. It also snapshots the substrate write epoch and estate counts before/after each measured case and the suite. A moving world invalidates the comparison.

### Versioned work matrix

`scripts/benchmark-forward-cases.json` currently includes deterministic zero-spread cases that vary the declared work envelope and interpretation pressure:

```text
What is a dog?          H=1 F=4
What is a dog?          H=2 F=8
What is a dog?          H=3 F=16
What is a pawn?         H=2 F=8   (ambiguous-sense fixture)
The opposite of hot is  H=2 F=8   (typed semantic-response fixture)
```

Each case pins steps, max stride, top-k, random seed, hops and fanout. The benchmark does not hardcode a desired prose answer merely to make a performance run pass. It fingerprints the semantic act/result so optimization runs can detect behavioral drift.

### One measured iteration

The harness deliberately separates planning, measured execution and semantic receipt retention:

```text
1. PRE-FLIGHT
   EXPLAIN (FORMAT JSON)
   exact generation.forward_program call
   no execution

2. MEASURE
   EXPLAIN (ANALYZE, BUFFERS, WAL, FORMAT JSON)
   same exact generation.forward_program call

3. RECEIPT REPLAY
   same deterministic read-only call once
   retain typed route/emit/terminal rows + semantic fingerprint
   replay time recorded separately and excluded from measured execution time
```

The replay exists because PostgreSQL `EXPLAIN ANALYZE` gives physical execution metrics but does not return the function rows to the harness. The deterministic replay is checked against the measured `Actual Rows`, and its terminal program/output/semantic-act fingerprint must remain identical across repeats. If the world moves between these phases, the case fails rather than pretending the runs are comparable.

### Preflight receipt

The preflight records the declared work ceiling directly from the exact program call:

```text
steps
hops H
fanout F
max stride
top-k
spread / deterministic seed
prior frontier scope
output-relation scope
```

It also retains PostgreSQL planner rows/cost/width. Planner cost is evidence about one physical provider; it is explicitly **not** declared to be Laplace billing currency.

This is an important current boundary: the benchmark now has a real before-execution plan receipt over the exact installed canonical program, but the native estimator does not yet predict every internal provider/candidate/CPU/I/O dimension before execution. #1425 owns that product estimator/calibration loop. Missing estimate dimensions remain missing rather than being fabricated from planner cost.

### Actual execution receipt

The measured `EXPLAIN ANALYZE` receipt retains, where PostgreSQL exposes them:

```text
actual rows / loops
server execution time
planning time
shared/local/temp blocks
I/O timing
WAL records/FPI/bytes
process-boundary wall time
RAPL-domain energy when available
```

The canonical forward trace replay preserves Laplace-native semantic work coordinates per routing round:

```text
route / emit / terminal rows
candidate count
ordered-context count
proposal-channel count
exact-channel count
sequence occurrence work
covered prompt occurrences
relation-family coverage
opposed/refuted occurrence coverage
support source/context breadth
routing rounds
required / satisfied / remaining obligations
completion / unresolved disposition
program id
output fingerprint
semantic-act id
output count
```

The harness derives plan-row estimate error only on the compatible planned-vs-actual row dimension. It does not flatten unlike structural/evidence dimensions into one impressive scalar.

### What `query-forward` proves and does not prove

A successful run proves that the exact selected installed runtime executed the versioned cases read-only, under the declared H/F/step/top-k boundaries, with the retained PostgreSQL and native forward receipts and stable semantic fingerprints.

It does **not** by itself prove that every intended COUPLE response plane is implemented, that every native/SPI boundary count is already externally visible, or that PostgreSQL planner cost is a calibrated customer price. #1401, #1561, #1425 and the relevant execution-grain owners remain the acceptance sources for those stronger claims.

The benchmark is designed to expose those missing dimensions instead of replacing them with token count.

## Sparse-compute law

The computational thesis is not “make dense math slightly faster.” It is to avoid world-sized/all-pairs work when indexed identity and typed providers can address a responding workset.

A benchmark making a complexity claim must name its variables and actual provider:

```text
world/population coordinate N
address/index provider and lookup behavior
admitted/responding work K
hops / fanout / frontier sizes
superlinear reductions/sorts/pairwise work over K, when present
```

Do not write `O(log N)+O(K)` as a universal slogan when a concrete operator uses a different index/algorithm.

## Query/cognition and billing work vocabulary

The benchmark vocabulary intentionally aligns with the product resource model:

```text
exact admitted root / prompt trajectory
world / evidence / source / time scope
hop budget H
fanout/frontier ceiling F_h
actual responders/candidates per hop
candidate reductions after filters/folds
relation/provider/operator families
containment/trajectory work
consensus/evidence cells
realization/output work
native/SPI/SQL/managed boundary calls and set sizes
CPU / memory / I/O / DB work
latency / energy where measured
semantic-act/result fingerprint
preflight estimates versus actual work
```

Not every coordinate is exposed by current code yet. The receipt schema grows when the actual executor exposes truthful counters; absent counters must not be guessed.

This is the benchmark form of the product rule: **one knowledge world, explicit compute envelope**. A cheaper request constrains computation; it does not secretly receive a deliberately less knowledgeable world.

## Optional accelerator / GPU law

GPU acceleration is optional sparse physical acceleration, not GPU-resident semantic authority.

CPU/GPU comparisons hold logical program, world/evidence epoch, selected identities, result contract and semantic output constant while recording provider identity, transfer bytes, device memory, timing, speedup and parity.

Installed GPU != selected GPU != GPU-resident world.

## Energy and power boundaries

The suite captures Intel RAPL domains when exposed.

- PSU nameplate wattage is capacity, not measured wall draw.
- RAPL is CPU/package/domain energy, not automatically whole-system wall energy.
- overlapping RAPL domains are not blindly summed into wall joules.
- whole-system energy requires a calibrated wall/PDU/UPS/BMC-compatible provider.

Any work-per-joule headline must align the work and energy intervals.

## Evidence artifact

Each dispatch attempts to upload a run/attempt-specific artifact containing, where selected/available:

- requested/resolved Git revision;
- registry + selected suite/profile identities;
- `scale-plan.json` and serviceable/saturation policy;
- build log;
- exact built core/T0 digests;
- exact built substrate extension version and execution-module identity;
- host/runner/storage/CPU-governor inventory;
- native linkage;
- accelerator state before/after;
- RAPL readings/deltas;
- raw profile logs;
- `WORK_INPUT` / `WORK_SHAPE` structural amplification;
- machine-readable scaling receipts;
- `query-forward.json` with preflight/EXPLAIN/typed forward receipts when `query` is selected;
- `suite-receipt.json`;
- Moby reconstructed bytes/digests when selected;
- manifest and file hashes.

Artifact upload uses `if: always()`. A host made unavailable by destructive saturation cannot be guaranteed to perform a terminal upload; that is another reason saturation is not the managed default.

## Isolation law

The workflow shares `laplace-shared-workspace` with delivery, so benchmark and deployment jobs cannot overlap on the persistent measured checkout.

Source/core profiles build the exact selected revision without installing/deploying/migrating/seeding it. `query` likewise does not install anything: it succeeds only when the currently installed content-versioned runtime already matches the exact selected build. This preserves the manual evidence lane's non-mutating contract.

## Forward suite growth

The common registry should continue adding explicit profiles for database-backed deposit/reconstruct, storage amplification, whole-corpus admission, cold/warm/perfcache reuse, CPU/GPU provider parity, complete accepted-work cognition/generation, model decomposition/export, competitor-equivalent accepted-work cost and calibrated whole-system energy.

Those profiles should feed the same plan/execution receipts used by estimator calibration, billing, capacity planning and optimization rather than creating a second performance vocabulary.
