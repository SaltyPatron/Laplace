## Cross-repository preservation law

When the same invention is implemented in more than one repository/generation, compare them against the **same higher-level semantic laws**, not against each other's accidents.

Useful coordination questions are:

```text
does each implementation preserve the same canonical content/composition?
does each preserve exact trajectory/occurrence/provenance?
does each expose the same typed evidence/standing semantics?
does each implement whole-observation coupling before unconstrained policy?
does each obey the same hop/fanout/resource contract?
does each keep repeated algorithmic work in coarse native/set execution?
does each emit comparable semantic/resource receipts?
```

Implementation details, schemas and ABIs may differ where their contracts permit it.

## What remains valuable from the original plan

The September 2 plan captured several durable delivery principles that remain valid:

- a source-tree fix is not the same as a deployed/live repair;
- derived-row freshness/cardinality is not automatically semantic-integrity proof;
- order-sensitive standing must be driven by declared event/recipe chronology rather than file/chunk/worker completion order;
- evidence durability and completion of derived folds are distinct states;
- a compatibility wrapper must not create a second semantic implementation;
- clean/source CI is insufficient when acceptance requires installed/live physical behavior;
- exact-head/artifact identity matters to proof;
- a logically correct result reached through a forbidden physical path remains an architecture defect when the physical path is part of acceptance.

Those principles have since been generalized in `AGENTS.md`, `INVENTION.md`, `ARCHITECTURE.md` and the operation/benchmark contracts.

## Current cross-repository coordination rule

If a present task genuinely spans both repositories:

- state the accepted semantic outcome first;
- identify which repository/runtime owns each required deployed behavior;
- preserve useful work in each without treating either implementation as the semantic authority;
- use current issue/PR state, not this dated plan, to determine dependencies;
- do not postpone an accepted repair in one product merely because another product may eventually replace it;
- do not duplicate implementation just to make both repositories look superficially identical when shared semantic contracts allow different physical designs.
